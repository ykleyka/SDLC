# Аутентификация через ASP.NET Core Identity

## Контекст и постановка задачи

Пользователи регистрируются по email и паролю. SRS требует надёжного хранения паролей (REQ-SEC-001), блокировки после неудачных попыток (REQ-SEC-006) и хранения минимума персональных данных (REQ-SEC-007). Внешние сервисы использовать нельзя (C-4).

Как реализовать регистрацию и вход, не написав собственную (и потенциально уязвимую) систему аутентификации?

## Драйверы решения

* Безопасное хэширование паролей и защита от перебора
* Отсутствие внешних сервисов
* Минимум собственного кода
* Совместимость с Blazor Server и EF Core

## Рассмотренные варианты

* ASP.NET Core Identity
* Собственная реализация (таблица пользователей + хэширование)
* Вход через внешнего провайдера (Google, GitHub OAuth)

## Итог решения

Выбранный вариант: «ASP.NET Core Identity», потому что он из коробки даёт хэширование PBKDF2, политику паролей, блокировку и cookie-аутентификацию, хранит данные в той же базе через EF Core и генерируется шаблоном Blazor Web App.

### Последствия

* Хорошо, потому что требования REQ-SEC-001 и REQ-SEC-006 выполняются настройкой `IdentityOptions`
* Хорошо, потому что страницы входа и регистрации генерируются шаблоном и только локализуются
* Плохо, потому что в БД появляются лишние таблицы Identity (роли, внешние логины), которые не используются
* Новое обязательство: в `ApplicationUser` добавляется поле `DisplayName`; подтверждение email отключается (почта не отправляется, C-4)

### Подтверждение

Тесты: пароль `abcdefg1` принимается, `abcdefgh` отклоняется; после 5 неверных паролей вход блокируется на 5 минут. Инспекция логов на отсутствие паролей и email (REQ-OBS-002).

## Плюсы и минусы вариантов

### ASP.NET Core Identity

* Хорошо, потому что проверенная библиотека Microsoft
* Хорошо, потому что всё нужное уже есть
* Плохо, потому что избыточная схема таблиц

### Собственная реализация

* Хорошо, потому что только нужные поля
* Плохо, потому что высокий риск ошибок в безопасности
* Плохо, потому что больше кода и тестов

### Внешний OAuth

* Хорошо, потому что пользователю не нужен новый пароль
* Плохо, потому что внешний сервис нарушает C-4
* Плохо, потому что не работает без интернета на демонстрации

## Дополнительная информация

Связано с C-3, REQ-SEC-001, 006, 007, REQ-COMP-002 SRS. Пересмотреть, если Заказчик захочет вход через соцсети.
