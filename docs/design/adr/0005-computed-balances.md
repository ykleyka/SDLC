# Балансы вычисляются при запросе, а не хранятся

## Контекст и постановка задачи

Баланс участника меняется при добавлении, изменении и удалении траты или погашения и при привязке виртуального участника. Сумма балансов группы всегда должна быть равна нулю (REQ-FUNC-014).

Хранить балансы в базе и обновлять их при каждой операции или вычислять каждый раз из трат и погашений?

## Драйверы решения

* Корректность: баланс не должен расходиться с тратами
* Производительность: расчёт ≤ 200 мс для 1000 трат и 30 участников (REQ-PERF-002)
* Простота кода изменяющих операций

## Рассмотренные варианты

* Вычислять при каждом запросе
* Хранить баланс в Members и обновлять при каждой операции
* Вычислять и кэшировать в памяти до следующего изменения

## Итог решения

Выбранный вариант: «Вычислять при каждом запросе», потому что он исключает рассинхронизацию балансов с тратами, а расчёт для максимальной группы занимает единицы миллисекунд (SDD 007-algorithms, 012-resources).

### Последствия

* Хорошо, потому что любая операция меняет только свои записи, балансы всегда верны
* Хорошо, потому что `BalanceCalculator` — чистая функция, легко тестируется
* Плохо, потому что экран «Мои группы» считает балансы для каждой группы пользователя; при большом числе групп понадобится оптимизация
* Нейтрально, потому что кэш можно добавить позже, не меняя схему БД

### Подтверждение

Модульный тест производительности: 1000 трат, 30 участников, расчёт балансов и переводов ≤ 200 мс (REQ-PERF-002). Тест на инвариант: для случайных наборов трат сумма балансов равна 0.

## Плюсы и минусы вариантов

### Вычислять при запросе

* Хорошо, потому что нет дублирования данных
* Хорошо, потому что нет ошибок обновления
* Плохо, потому что повторные вычисления

### Хранить в Members

* Хорошо, потому что баланс читается мгновенно
* Плохо, потому что каждая операция должна правильно обновить несколько балансов; ошибка ломает данные навсегда
* Плохо, потому что изменение траты требует «откатить» старые доли и применить новые

### Кэш в памяти

* Хорошо, потому что быстрее при частых просмотрах
* Плохо, потому что сложность инвалидации без заметной выгоды при текущих объёмах

## Дополнительная информация

Связано с REQ-FUNC-004, 014, REQ-PERF-002 SRS. Пересмотреть, если расчёт для экрана «Мои группы» превысит 200 мс.
