# Жадный алгоритм построения списка переводов

## Контекст и постановка задачи

Главная ценность EvenUp — показать, кто кому сколько перевести, чтобы закрыть все долги минимумом переводов (BG-2). SRS требует не более N − 1 переводов, где N — число участников с ненулевым балансом (REQ-FUNC-015). Найти абсолютный минимум переводов — NP-трудная задача (сводится к разбиению множества на подмножества с нулевой суммой).

Каким алгоритмом строить список переводов, чтобы выполнить требование и уложиться в 200 мс (REQ-PERF-002)?

## Драйверы решения

* Гарантия не более N − 1 переводов
* Время работы для 30 участников — миллисекунды
* Понятный результат для пользователя
* Простота реализации и тестирования

## Рассмотренные варианты

* Жадный: наибольший должник платит наибольшему кредитору
* Точный перебор подмножеств с нулевой суммой
* Прямые переводы по каждой трате (без упрощения)

## Итог решения

Выбранный вариант: «Жадный», потому что он гарантирует не более N − 1 переводов (на каждом шаге обнуляется хотя бы один участник), работает за O(N²) и на практике в большинстве случаев даёт минимальное число переводов.

### Последствия

* Хорошо, потому что алгоритм занимает ~20 строк и полностью покрывается модульными тестами
* Хорошо, потому что результат детерминирован: при равных балансах порядок определяется `Member.Order`
* Плохо, потому что в редких случаях получается на 1–2 перевода больше теоретического минимума (например, когда группа распадается на независимые подгруппы)
* Новое обязательство: консольный прототип на примере Приложения Б и случайных данных (REQ-POC-002)

### Подтверждение

Модульные тесты `SettlementTests`: пример Приложения Б даёт 2 перевода; для 10 000 случайных наборов балансов после применения переводов все балансы нулевые, а число переводов ≤ N − 1.

## Плюсы и минусы вариантов

### Жадный

* Хорошо, потому что быстрый и простой
* Хорошо, потому что выполняет требование N − 1
* Плохо, потому что не всегда абсолютный минимум

### Точный перебор

* Хорошо, потому что абсолютный минимум
* Плохо, потому что экспоненциальная сложность: для 30 участников 2³⁰ подмножеств, не укладывается в 200 мс
* Плохо, потому что сложно тестировать

### Переводы по каждой трате

* Хорошо, потому что очевидно, откуда взялся каждый перевод
* Плохо, потому что число переводов растёт с числом трат и не выполняет REQ-FUNC-015

## Дополнительная информация

Связано с BG-2, REQ-FUNC-015, REQ-PERF-002, REQ-POC-002 SRS и SDD 007-algorithms. Пересмотреть, если пользователи будут жаловаться на «лишние» переводы: можно добавить точный поиск для групп до 12 участников.
