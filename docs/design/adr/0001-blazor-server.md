# Интерфейс на Blazor Web App в режиме Interactive Server

## Контекст и постановка задачи

EvenUp — интерактивное веб-приложение: формы трат, мгновенный пересчёт балансов, переключение вкладок группы. Основную разработку выполняет один человек, знающий C#, а junior привлекается к ограниченным UI-задачам и проверкам. Ограничение C-1 SRS требует .NET 10.

Какую модель веб-интерфейса выбрать, чтобы быстро сделать интерактивный UI на C# и не писать отдельный API?

## Драйверы решения

* Скорость разработки основным разработчиком при ограниченном участии junior (сроки учебного проекта)
* Один язык (C#) для интерфейса и логики
* Безопасность: проверка прав только на сервере (REQ-SEC-002)
* Работа с телефона по обычному браузеру (REQ-PORT-002)
* Отклик ≤ 1 с при 20 пользователях (REQ-PERF-001)

## Рассмотренные варианты

* Blazor Server (Blazor Web App, Interactive Server)
* Blazor WebAssembly + ASP.NET Core Web API
* ASP.NET Core MVC / Razor Pages + JavaScript

## Итог решения

Выбранный вариант: «Blazor Server», потому что он даёт интерактивный UI полностью на C# без отдельного API и DTO-слоя для сети, бизнес-логика и данные не покидают сервер, а ограничения режима (постоянное соединение, память на сеанс) несущественны при 20 пользователях.

### Последствия

* Хорошо, потому что сервисы вызываются из компонентов напрямую через DI, без HTTP-контроллеров
* Хорошо, потому что код и данные не передаются в браузер, страница загружается быстро и на слабом телефоне
* Плохо, потому что нужен постоянный WebSocket; при обрыве связи интерфейс переподключается (A-2, REQ-REL-004)
* Плохо, потому что состояние каждого пользователя хранится в памяти сервера; горизонтальное масштабирование потребует sticky sessions (не нужно по REQ-DIST-001)
* Новое обязательство: `DbContext` создаётся через фабрику на каждую операцию (SDD 009-concurrency)

### Подтверждение

Проект создаётся шаблоном `dotnet new blazor --interactivity Server --auth Individual`. Прототип REQ-POC-001 проверяется на ПК и телефоне. На код-ревью проверяется, что компоненты не используют `DbContext` напрямую.

## Плюсы и минусы вариантов

### Blazor Server

* Хорошо, потому что один проект и один язык
* Хорошо, потому что нет отдельного API, который нужно защищать
* Нейтрально, потому что нужен сервер .NET (он нужен в любом варианте)
* Плохо, потому что зависит от стабильного соединения

### Blazor WebAssembly + Web API

* Хорошо, потому что UI работает в браузере и меньше нагружает сервер
* Плохо, потому что нужно писать и защищать REST API и дублировать проверки
* Плохо, потому что первая загрузка — несколько мегабайт, медленно на телефоне

### ASP.NET Core MVC + JavaScript

* Хорошо, потому что зрелая и простая серверная модель
* Плохо, потому что интерактивность (пересчёт, диалоги) пришлось бы писать на JavaScript
* Плохо, потому что каждое действие — перезагрузка страницы или ручной AJAX

## Дополнительная информация

Связано с ограничением C-1, допущениями A-2, A-3 и требованиями REQ-REL-004, REQ-PERF-001 SRS. Решение стоит пересмотреть, если понадобится офлайн-режим или нагрузка вырастет до сотен одновременных пользователей.
